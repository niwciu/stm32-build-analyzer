# LLVM adapter design

## Decision

The LLVM adapter executes `llvm-objdump` and `llvm-nm` through the existing
bounded, cancellable object-tool workflow. It uses two LLVM-specific parsers:

- `LlvmObjectParser` reads the `Type`-based section table emitted by
  `llvm-objdump -h` and the GNU-compatible records emitted by `llvm-nm`;
- `LlvmLldMapParser` validates LLD's native
  `VMA LMA Size Align Out In Symbol` MAP format and reads region origins and
  capacities from materialized linker-script `MEMORY` declarations.

The shared workflow remains responsible for tool resolution, timeouts, output
limits, cancellation, safe executable copies, partial results when `llvm-nm`
fails, diagnostics, and provenance.

## Why this boundary

Native LLD MAP output describes output sections and symbols but does not emit
GNU ld's `Memory Configuration` capacity table. `llvm-objdump` exposes section
VMA, LMA, size, and allocation type, but it also cannot recover a region's total
capacity. A selected linker script is therefore required for accurate usage
percentages.

Reusing the GNU MAP parser would incorrectly reject native LLD output. Using a
new ELF library would duplicate the already bounded object-tool workflow and
would still not provide linker-script region capacity. Dedicated format parsers
behind the existing injected interfaces keep those concerns explicit.

## Supported scope

The verified scope is ELF output linked by LLD with its native MAP header,
`llvm-objdump`/`llvm-nm` output, and one or more materialized linker scripts whose
`MEMORY` entries use numeric hexadecimal or decimal `ORIGIN` and `LENGTH`
literals with optional `K`, `M`, or `G` suffixes. The real regression fixture is
a freestanding Arm Cortex-M4 build generated by Clang and LLD 18.1.3.

The provider automatically looks for a single unambiguous linker script beside
the selected MAP/ELF files and then in their parent directories up to the
workspace root. A script whose basename matches the selected build output wins
over other candidates. The search only accepts `.ld`, `.lds`, and `.ldscript`
files containing a `MEMORY` block, never scans outside the workspace, and does
not guess when multiple candidates remain. Selected scripts are watched along
with the MAP and ELF files.

Computed linker-script expressions, preprocessor placeholders, scripts without
`MEMORY`, non-ELF formats, and GNU-style MAP files produced while using Clang
remain unsupported until separate fixtures and parsing rules are approved.
